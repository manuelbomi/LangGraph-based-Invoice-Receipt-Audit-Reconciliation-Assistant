# Sample data

Everything in this folder is **synthetic** -- fictitious vendors, fictitious
amounts, a fictitious client company ("Meridian Analytics LLC"). It was
generated by [`scripts/generate_samples.py`](./scripts/generate_samples.py)
(reportlab for the PDFs, PIL for the receipt images, openpyxl for the
ledger), not sourced from any real company's documents.

Two reasons for that, deliberately:

1. **Copyright** -- real invoice templates from real vendors (or SaaS
   billing tools) are typically proprietary designs; scraping one to use as
   a "demo" template would not be a clean thing to redistribute in a public
   repo.
2. **Privacy / data protection** -- real invoices and receipts contain real
   people's and companies' financial data. There is no reason a public
   tutorial repo needs to touch anyone's actual transactions.

Regenerate everything at any time with:

```bash
pip install reportlab pillow openpyxl   # already in backend/requirements.txt
python sample-data/scripts/generate_samples.py
```

## What's here

### `invoices/` (4 PDFs, 3 distinct layouts)

| File | Vendor | Total | Layout |
|---|---|---|---|
| `INV-1001_bright_office_supplies.pdf` | Bright Office Supplies Inc. | $1,266.53 | Letterhead-style header, bordered table |
| `INV-1006_bright_office_supplies_DUPLICATE.pdf` | Bright Office Supplies Inc. | $1,266.53 | Same layout, **same vendor + amount, 2 days later** |
| `INV-2044_summit_cloud_hosting.pdf` | Summit Cloud Hosting LLC | $3,518.13 | Centered header, minimalist unbordered table |
| `FM-778_redwood_facilities.pdf` | Redwood Facilities Maintenance | $612.75 | Compact, top-right meta, shaded rows |

`INV-1006` is an intentional near-duplicate of `INV-1001` (same vendor,
same total, invoice date two days apart, different invoice number) -- a
realistic "the vendor's invoice got keyed into AP twice" scenario. Both are
posted to the general ledger below, so running either invoice back through
the app's reconcile step surfaces a **duplicate-payment finding**, the
headline audit finding this tutorial demonstrates. `FM-778` deliberately has
**no corresponding ledger entry**, to demonstrate the "no matching ledger
entry found" finding.

### `ledger/general_ledger.xlsx`

A 6-row general ledger / expense register (`date`, `vendor`, `description`,
`gl_account`, `amount`, `currency`):

- Rows 1-2: the `Bright Office Supplies Inc.` duplicate pair described above.
- Row 3: the `Summit Cloud Hosting LLC` payment (**exceeds the $3,000 policy
  approval threshold** used by the demo -- see `reconcile_node`).
- Row 4: the `Metro Taxi Co` travel expense (matches the taxi receipt).
- Rows 5-6 (`Acme Legal Services`, `Statewide Insurance Co`): realistic,
  unrelated GL activity with **no corresponding invoice or receipt in this
  sample set**. They exist so that fuzzy vendor/amount matching has
  plausible near-neighbors to correctly *not* match against (a true-negative
  check), in addition to `FM-778` proving the true-positive "no match found"
  case.

This ledger is loaded into Postgres by `backend/scripts/seed_ledger.py`
(from the bundled `.xlsx`, via `pandas`/`openpyxl`) -- see the backend
README section for how it's wired into the `reconcile` graph node.
